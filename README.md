# Idempotent Payments API (Python / FastAPI)

A small payments backend that cannot be tricked into double-charging a
user, even when the same request arrives multiple times at once
(network retries, double-clicks, etc).

## The concept, in one paragraph

Every payment request carries an `idempotency_key` generated by the
client. If the same key arrives twice, the second request should return
the result of the FIRST one, not create a second charge. The naive way
("check if key exists, then insert if not") has a race condition: two
requests can both check at the same time, both see "doesn't exist," and
both insert. The fix is making check-and-insert ONE atomic database
operation instead of two separate steps. Full before/after comments are
in `app/payments.py` -- read that file first.

## Setup (run this on your Mac)

### 1. Confirm Python is installed
```
python3 --version
```
You already have this on macOS by default.

### 2. Make sure Postgres is running
(You should already have this from the earlier Go setup. If not:)
```
brew install postgresql@15
brew services start postgresql@15
createdb payments
```

### 3. Load the schema
From inside this project folder:
```
psql payments -f app/schema.sql
```

### 4. Create a virtual environment and install dependencies
```
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```
(You'll need to run `source venv/bin/activate` every time you open a
new terminal to work on this project.)

### 5. Run the server
```
uvicorn app.main:app --reload --port 8000
```
You should see it start on http://localhost:8000. Visit
http://localhost:8000/docs in your browser -- FastAPI auto-generates
an interactive API tester, which is genuinely useful for demoing this
in an interview.

### 6. Test a single payment
```
curl -X POST http://localhost:8000/payments \
  -H "Content-Type: application/json" \
  -d '{"idempotency_key":"abc123","user_id":"user-1","amount_cents":1000}'
```

### 7. Run the concurrency proof
In a second terminal (with the server still running, venv activated):
```
python race_test.py --n 50
```
Expected output: `New payments created: 1` and `PASS: no double-charge occurred.`

This is the number for your resume, e.g.:
"Fixed a race condition allowing duplicate charges; verified zero
duplicate payments across 50 concurrent identical requests."

## What to actually understand (not just run)

1. **Why "check, then insert" is unsafe** across two separate database
   round-trips -- the gap between them is where the bug lives.
2. **What `ON CONFLICT DO NOTHING` does** -- Postgres guarantees this
   whole operation is atomic, so no request can "sneak in" mid-way.
3. **The alternative approach**: `SELECT ... FOR UPDATE` (row-level
   locking). Worth reading about, since interviewers may ask you to
   compare it to the `ON CONFLICT` approach you used.
4. **Why real payment systems (Stripe, Razorpay) use this exact
   pattern** -- look up "Stripe idempotency keys" to see it's not a
   toy concept.
